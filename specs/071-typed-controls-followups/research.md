# Phase 0 Research: Typed-Controls-Migration Follow-Ups (071)

No `NEEDS CLARIFICATION` markers remained in the Technical Context. The spec is a
precise completion of named `070` tasks against existing mechanisms; research here
records the concrete decisions for reusing those mechanisms, with the
alternatives that were rejected.

## R1 — Extend `catalogFacts` from 6 to 47 (single source)

- **Decision**: Add the 41 missing controls as `TypedCatalogFact` records to
  `CatalogGen.catalogFacts`, populating each from the values that the
  corresponding hand-maintained row already carries in `catalog.yml` / `Catalog.fs`
  (id, display name, category, module, purpose, required attributes, events,
  accessibility role). Then regenerate via
  `./fake.sh build -t RefreshSurfaceBaselines`, which splices each row into its
  `BEGIN/END GENERATED: typed-catalog/<id>` region in both files.
- **Rationale**: `CatalogGen` is already the single-source generator for the 6
  reference facts; the renderer + currency machinery (`render`, `currency`,
  `isCurrent`, `currencyDrift`) is fact-count-agnostic, so the 6→47 step is data,
  not a new mechanism (spec Assumptions). The generated bytes must equal the
  existing hand-maintained bytes so the regeneration diff for those 41 rows is
  empty except for the inserted markers (FR-002, edge case "marker insertion is
  generated, not hand-placed").
- **Alternatives considered**: (a) Generate only a subset and leave the rest
  hand-maintained — rejected: SC-001 requires 100% generated, zero hand-maintained.
  (b) Introduce a new generation mechanism / different marker scheme — rejected:
  spec Assumptions mandate reusing the existing per-row marker + special-case
  machinery as-is.

## R2 — Generalize the `renderFSharpRow` chart/data-grid evidence special-case

- **Decision**: Replace the single-id guard `if fact.Id = "data-grid"` with
  membership in the set of evidence-carrying ids:
  `data-grid`, `line-chart`, `bar-chart`, `pie-chart`, `scatter-plot`,
  `graph-view`. Those six rows append `|> withChartDataGridEvidence`; the
  YAML renderer's chart/data-grid evidence path (`ymlChartDataGridEvidence`)
  extends to the same set.
- **Rationale**: `grep withChartDataGridEvidence src/Controls/Catalog.fs` shows
  exactly those six rows carry the extra evidence pointer today (lines 104, 128,
  130, 132, 134, 136). Preserving the pointer for the chart/graph + DataGrid family
  is mandated by FR-004 and the "Chart/DataGrid evidence special-case" edge. A set
  membership keeps the renderer a pure function of the fact.
- **Alternatives considered**: (a) Move the evidence flag onto `TypedCatalogFact`
  as a field — cleaner long-term, but it changes the fact record shape and the 6
  existing fixtures; a set keyed by id is the minimal, fixture-stable change and is
  recorded here as the chosen trade-off (a field could follow in a later refactor).
  (b) Hand-add the pointer post-generation — rejected: violates "generated, never
  hand-edited" (FR-002).

## R3 — `custom-control` bridge-typed row

- **Decision**: Generate `custom-control`'s row from a `TypedCatalogFact` whose
  `RequiredAttributes = []` (no fabricated required attribute), matching its
  bridge-typed classification in `070`'s standalone cross-check (T036), where it is
  the one migrated control with no `Props` schema (`Widget.ofControl`).
- **Rationale**: FR-006 and edge case require `custom-control` to generate a valid
  row without inventing a required attribute it does not have. `TypedMigrationTests`
  asserts `typedPropsById.Count = 40` (the 41st, `custom-control`, is schema-free)
  while `rowsById.ContainsKey "custom-control"` — the catalog still lists it. The
  generated row mirrors the existing hand-maintained `custom-control` row's bytes.
- **Alternatives considered**: Synthesize a placeholder required attribute to make
  it uniform — rejected: contradicts FR-006 and would break the T036 bridge
  classification.

## R4 — `066` fixture-iteration cross-check stays green over 47

- **Decision**: For each of the 41 newly-generated ids, capture two golden parity
  fixtures — `Catalog.fs.<id>.txt` and `catalog.yml.<id>.txt` — into the
  pre-existing `specs/066-typed-catalog-generation/readiness/parity-fixtures/`
  directory (where `CatalogTests.fs` reads them, by `fact.Id`), produced **from**
  `CatalogGen.renderFSharpRow` / `renderYamlRow` output (golden capture, not
  hand-typed). Extend the hand-maintained `typedPropsById` map in `CatalogTests.fs`
  to all typed ids so the "`catalogFacts` ids == typed ids" and "each
  `requiredAttribute` PascalCased ∈ `Props` fields" assertions hold for the full
  set (with `custom-control` excluded from the Props-field assertion as bridge-typed
  per R3).
- **Rationale**: FR-005 / SC-003. The test iterates `for fact in catalogFacts`
  reading one fixture per id; a 47-fact table without fixtures fails on the first
  missing fixture (edge case "Fixture count"). Capturing fixtures from real
  generator output keeps them honest (no synthetic literal) and makes the parity
  assertion meaningful — it guards future drift of the renderer.
- **Alternatives considered**: (a) Relax the test to iterate only the original 6 —
  rejected: weakens the cross-check, violates the spirit of SC-003 and
  Principle VI (never weaken an assertion to green a build). (b) Place fixtures
  under the `071` readiness folder — rejected: the test path is hardcoded to the
  `066` fixtures dir; moving it is an unnecessary test edit. Fixtures live where the
  reader reads.

## R5 — Typed gallery panel: ≥1 control per mechanic group

- **Decision**: Extend the existing `typedAuthoringPanel` in
  `samples/ControlsGallery/Program.fs` (today TextBlock + Button + CheckBox) to
  cover one control from each mechanic group, authored **only** through
  `FS.Skia.UI.Controls.Typed.*` `view` functions (no `Attr` / `*.create` call in
  the panel). Representative coverage of the categories present in the catalog:
  display (`TextBlock`), input (`Button`/`TextBox`), stateful input
  (`TextArea`), layout container (`Stack`), navigation/composite (`Tabs`/`Toolbar`),
  overlay (`Tooltip`/`Dialog`), selection collection (`ListBox`/`ComboBox`),
  charts/graph (`LineChart`/`GraphView`).
- **Rationale**: FR-007 / SC-004. The panel is a render/interaction smoke over the
  migrated surface, deliberately bounded (edge "Gallery panel breadth vs. launch
  cost"); per-control parity already lives in `070`'s suites. Reusing the existing
  panel keeps it alongside the other gallery panels (acceptance scenario 2).
- **Alternatives considered**: A separate new panel module — rejected: the spec
  says *extend the existing* persistent panel (FR-007); a parallel panel adds launch
  cost without benefit. Full per-control coverage — rejected: out of scope, the
  panel is representative by design.

## R6 — Rendering / accessibility coverage at ≥2 viewports

- **Decision**: Add cases to `RenderingTests.fs` and `AccessibilityTests.fs` that
  render the typed gallery panel at ≥2 viewport sizes and assert no diagnostics /
  the expected accessibility roles, mirroring the existing "render output covers
  viewport sizes" and typed-vs-legacy parity test shapes already in
  `RenderingTests.fs`.
- **Rationale**: FR-008 / SC-005. `070`'s parity guarantee makes these suites
  transparent to the typed surface (typed `view` lowers to the same IR), so the new
  cases exercise the panel through the same authoritative render path — no new
  render/Skia/Vulkan behavior is introduced (070 `controls-rendering.md`).
- **Alternatives considered**: One viewport only — rejected: spec requires ≥2.
  A new bespoke render harness — rejected: reuse the existing suites' headless
  render path.

## R7 — Deterministic render-only evidence

- **Decision**: Capture typed-gallery viewport render evidence to
  `specs/071-typed-controls-followups/readiness/controls-rendering.md`, render-only,
  with the determinism (byte-identical re-capture) claim stated, and **no** `[S]`
  synthetic disclosure. Mirror the structure of `070`'s `controls-rendering.md`,
  upgrading its "Deferred (tracked)" section to "delivered here".
- **Rationale**: FR-009 / SC-006. The lowering is pure (no wall-clock/random/I/O),
  so re-rendering identical `Props` (and, for stateful controls, identical model
  state) yields byte-identical IR — the evidence is real, not synthetic, and not a
  substitute for the persistent gallery launch (edge "Render evidence is
  render-only").
- **Alternatives considered**: Treating captured frames as `[S]` synthetic —
  rejected: it is real render output, `[S]` disclosure would be dishonest in the
  other direction and would (correctly) fail SC-006's "no `[S]`" requirement.

## R8 — Surface & routing impact

- **Decision**: Treat the package surface as **Tier 2** — additive-only or empty
  per-package surface delta for `FS.Skia.UI.Controls` (the 41 typed modules already
  shipped in `070`); regenerate the per-package baseline only if the diff shows it
  is empty/additive, verified by `PackageSurfaceCheck` / `PerPackageSurfaceDiff`.
  Re-run `./fake.sh build -t Route` on the implementation diff and run exactly the
  gates it prints, FAKE-backed gates sequentially.
- **Rationale**: FR-010 / SC-007 / SC-008. The implementation diff (build fact
  table + generated artifacts + tests + sample + fixtures) re-routes from the
  current spec-only `docs-only` classification; the governance-artifact change is
  expected to add `ControlsCatalogGenerationCheck` to the printed set.
- **Alternatives considered**: Assume the spec-only Route output is final —
  rejected: Route reads the working-tree diff, which changes once code lands; the
  plan explicitly requires re-running it.
