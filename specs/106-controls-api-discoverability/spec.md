# Feature Specification: Controls Authoring API Discoverability

**Feature Branch**: `106-controls-api-discoverability`  
**Created**: 2026-06-12  
**Status**: Draft  
**Input**: User description: "fix that problem comprehensively with all fixes."

> **Problem origin.** While consuming the published library through a project
> generated by `dotnet new fs-skia-ui`, a coding agent had to resort to
> **reflection over the compiled DLL** to author Controls correctly. Diagnosis
> found this is not a single missing file but a compound discoverability failure
> in the Controls authoring surface as a whole:
>
> 1. **The public surface is documented with boilerplate.** Almost every public
>    member of the legacy authoring API (the `Attr`/control builders such as
>    `text`, `value`, `width`, `onClick`) and the `Catalog` discovery API carries
>    the same placeholder summary — *"Public contract function exposed by this
>    FS.Skia.UI package."* — which ships in the package `.xml` and therefore in
>    IntelliSense, telling a consumer the signature but nothing about meaning,
>    behavior, or which controls accept which attribute.
> 2. **The discoverable, compiler-checked front door is hidden.** A typed Props
>    front door (`FS.Skia.UI.Controls.Typed`, per-control `Props<'msg>` records +
>    `view` functions) exists and is comparatively well-documented, but the
>    generated template starter demonstrates only the stringly-typed legacy
>    builder API, so neither a human nor an agent discovers the path where the
>    compiler would guide authoring.
> 3. **Per-control facts are buried.** The `catalog.yml` describing every
>    control's required/supported attributes, events, visual states, and typed
>    module is packed into `contentFiles/` and is not surfaced through
>    IntelliSense, the README, or any documented discovery mechanism, and the
>    programmatic `Catalog.*` API that exposes the same facts is itself
>    boilerplate-documented.
>
> `.fsi` source files are intentionally **not** shipped inside F# NuGet packages
> (only the compiled DLL + `.xml`); that is standard and out of scope to change.
> The fix targets what a consumer *can* see — the `.xml` doc text shown in
> IntelliSense, the template starter code, the bundled in-repo API reference, and
> the documented discovery mechanism — so reflection is never the most reliable
> path again.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Compiler-guided authoring is the demonstrated default (Priority: P1)

A developer (or their coding agent) generates a project with
`dotnet new fs-skia-ui` and opens the starter view to learn how to build a UI
with controls. The starter demonstrates the **typed Props front door** as the
primary way to author controls: each control is constructed from an immutable,
compiler-checked `Props<'msg>` record whose field names and types tell the author
exactly what the control accepts. Authoring a new control is a matter of filling
in record fields the compiler enumerates and checks — not guessing stringly
attribute names or reflecting over the DLL.

**Independent test**: From a freshly generated template project, an author (or
agent) adds a second control of a different kind using only the typed front door
shown in the starter and the IntelliSense field list — with no reflection, no
repository source inspection, and no trial-and-error attribute guessing — and it
compiles and renders. The generated starter compiles and its controls render.

### User Story 2 - IntelliSense explains the authoring surface (Priority: P2)

A developer hovers any public member of the Controls authoring surface (a typed
`Props` field, a typed control `view`/`create` function, a legacy `Attr` builder,
or a `Catalog` discovery function) and sees a substantive description: what it
does, what its value means, and — for attributes — which control kinds accept it.
No public authoring member shows the placeholder *"Public contract function
exposed…"* boilerplate. Because this text ships in the package `.xml`, the same
guidance is available to an offline agent reading the package, not only to an IDE.

**Independent test**: For every public member of the Controls authoring surface,
the shipped XML documentation contains a non-placeholder summary (no occurrence of
the known boilerplate sentence and no empty/duplicate-only summaries on the
authoring surface). A governance check enumerates the surface and fails if any
member carries placeholder or missing documentation.

### User Story 3 - Per-control facts are discoverable without reflection (Priority: P3)

A developer or agent needs to know which attributes/events a specific control
supports. They reach this from a documented, discoverable mechanism — a
programmatic discovery API whose own documentation explains how to enumerate a
control's required and supported attributes, its events, its visual states, and
its typed module — plus an in-repo, consumer-visible catalog reference that the
generated project's README points to. The answer is obtained by reading shipped
docs or calling the documented discovery API, never by reflecting over the
assembly.

**Independent test**: Starting from the generated project's README, a consumer
follows a documented pointer to (a) the discovery API and (b) the bundled
per-control catalog reference, and from either one determines the complete
supported-attribute set for a named control without inspecting the DLL via
reflection or reading framework source.

### Edge Cases

- A control with optional event fields (e.g. a button whose click handler is
  `None`) must remain authorable through the typed front door with the
  no-handler case clearly documented, so the consumer does not have to discover
  the "omit to bind nothing" behavior by experiment.
- Controls that are not yet migrated to the typed front door must still be
  reachable: the discovery mechanism and docs must not imply a control is
  unsupported merely because it lacks a typed module.
- A consumer authoring against the **host** seam (running an interactive app)
  must be able to discover that surface too, not only the control-construction
  surface — the host front door is part of "authoring a controls app."
- The boilerplate-detection governance check must not fire on legitimately short
  but meaningful summaries, and must not be satisfied by mechanically reworded
  placeholders that still carry no semantic content.

## Requirements *(mandatory)*

### Functional Requirements

#### Demonstrated typed front door (US1)

- **FR-001**: The generated template starter view MUST author its controls
  through the typed Props front door (`FS.Skia.UI.Controls.Typed`) as the primary,
  demonstrated API, replacing the stringly legacy-builder usage currently shown.
- **FR-002**: The starter MUST demonstrate enough variety (at minimum: a display
  control, an interactive input control, and a button with an event handler) that
  a consumer can generalize to other controls by analogy.
- **FR-003**: The generated starter MUST compile and its controls MUST render
  through the existing render path with no behavior regression versus the current
  starter.
- **FR-004**: The typed front door surface that the starter relies on MUST be
  present in the generated project's in-repo API reference (`docs/api-surface/`),
  so the consumer has the typed `Props`/`view` signatures on disk without
  reflection. The typed surface is already enrolled in surface-baseline generation
  (feature 089); this feature MUST confirm that enrollment holds and keep the
  bundle current so the surface cannot silently drift out of the reference.

#### Documented authoring surface (US2)

- **FR-005**: Every public member of the Controls authoring surface MUST carry a
  substantive XML doc summary describing its purpose and, for attribute/prop
  members, the meaning of its value and which control kinds accept it. The
  authoring surface comprises, at minimum: the legacy `Attr` builder functions,
  the legacy per-control `create`/builder entry points, the typed `Props` record
  fields and per-control `view` functions, and the `Catalog` discovery API.
- **FR-006**: No public member of the Controls authoring surface MAY retain the
  placeholder boilerplate summary (the *"Public contract function exposed by this
  FS.Skia.UI package."* sentence) or an empty summary.
- **FR-007**: A governance gate MUST enumerate the Controls public authoring
  surface and FAIL when any member carries placeholder, empty, or
  duplicate-only-placeholder documentation, so the documented surface cannot
  regress to boilerplate. The gate MUST live in the single governance home and be
  wired into the routed gate set for Controls public-surface changes.
- **FR-008**: The improved documentation MUST be carried in the shipped package
  `.xml` (i.e. authored as `///` doc comments on the public surface), so the
  guidance reaches both IDE IntelliSense and an agent reading the package
  offline.

#### Discoverable per-control facts (US3)

- **FR-009**: The programmatic discovery API (the `Catalog` module functions that
  report a control's required attributes, supported attributes, supported events,
  visual states, and typed module) MUST itself be documented well enough that a
  consumer can use it to enumerate a control's authoring contract from
  IntelliSense alone.
- **FR-010**: The generated project MUST surface, from its README (or an equally
  prominent generated entry point), a documented pointer to (a) the programmatic
  discovery API and (b) a consumer-visible per-control catalog reference, so a
  consumer knows the discovery mechanism exists without reading framework source.
- **FR-011**: The per-control catalog facts MUST be available to a consumer in a
  consumer-visible location (not only buried in package `contentFiles/`), such
  that the README pointer resolves to something the consumer can actually open
  and read in their generated project.
- **FR-012**: The interactive host authoring seam (the entry point a consumer uses
  to run an interactive controls app) MUST be covered by the same discoverability
  guarantees — demonstrated and/or documented and reachable from the README — so
  "authoring a controls app" is discoverable end to end, not just control
  construction.

#### Anti-reflection guarantee (cross-cutting)

- **FR-013**: The generated template's authoring guidance MUST NOT instruct
  consumers to avoid reflection while leaving the documented alternative empty:
  every place that discourages reflection/source inspection MUST resolve to a
  concrete, populated, consumer-visible reference (typed front door in the
  starter, documented IntelliSense, discovery API, and catalog reference).

> Interacting / conflicting requirements: FR-001 makes the **typed** front door
> the demonstrated default, while FR-005/FR-006 require the **legacy** builder
> surface to also be fully documented. Resolution: both hold — the legacy surface
> remains supported and fully documented for consumers who use it, but the starter
> leads with the typed front door as the recommended, compiler-guided path. The
> legacy API is documented, not demonstrated; the typed API is both.

### Framework Governance Prompts *(mandatory)*

> **Exempt from the "no implementation details" rule (feature 085, FR-014).** This
> section is *expected* to name concrete packages, `.fsi` signatures, build
> targets, and evidence paths.

- **Package impact**: No package identity changes. Package **contents** change:
  improved `///` documentation flows into the shipped `FS.Skia.UI.Controls.xml`
  (and any other affected package `.xml`); the typed front door surface is
  enrolled into surface-baseline generation; a consumer-visible per-control
  catalog reference is bundled into the generated template. The active controls
  package path (`FS.Skia.UI.Controls`, with the interactive host in
  `FS.Skia.UI.Controls.Elmish`) is the surface in scope; no legacy Charts package
  migration is involved. Version bump on merge per the standard pack flow.
- **Public contract impact**: No change to the **shape** of any public `.fsi`
  signature is required by the documentation work; however `///` doc comments are
  added across the public Controls authoring surface (which lives in the `.fsi`
  files and `.fs` where applicable), and the typed front door is newly enrolled
  in `docs/api-surface/` bundling and surface baselines. Sample/template contracts
  change (the starter `View`). Any added doc-only `.fsi` edits and the new
  governance gate escalate routing to the controls-public-surface set.
- **State workflow impact**: None. No change to stateful workflow, I/O, commands,
  effects, subscriptions, or interpreter behavior. Rendering output is unchanged
  (the starter migrates to the typed front door, which lowers structurally to the
  same controls).
- **Layout/rendering impact**: None intended — the typed front door lowers to the
  same lowered control IR, so the generated starter renders equivalently. No
  Vulkan/Skia/screenshot/visual-output change is in scope beyond the starter
  rendering the same controls it does today.
- **Evidence obligations**: Generated-product check showing the regenerated
  starter compiles and renders; template check; the new documentation-coverage
  gate's report enumerating the authoring surface with zero placeholder/empty
  findings; surface-baseline currency for the newly bundled typed front door;
  per-control catalog reference present in the generated project; EvidenceGraph +
  EvidenceAudit (0 synthetic) for the routed set.
- **Unsupported scope**: Shipping `.fsi` source inside the NuGet package (F# does
  not do this; out of scope). A full from-scratch fsdocs HTML site is not required
  by this feature. Migrating **all 52** controls to the typed front door is out of
  scope — only the starter's demonstrated set must use it; the rest stay reachable
  and documented. No redesign of the controls model (no XAML/data-binding/
  dependency-properties — permanent non-goals).
- **Build-target impact**: `GeneratedProductCheck` and `TemplateCheck` exercise
  the regenerated starter and bundled reference; a **new** documentation-coverage
  gate is added to the governance home and the routed Controls public-surface set
  (and to the generated `validation.contract.yml` via `Routing.fs`);
  `RefreshSurfaceBaselines` regenerates baselines for the newly enrolled typed
  surface; `EvidenceGraph`/`EvidenceAudit` run for the escalated path. `Dev`
  builds the doc comments and the new gate.

## Success Criteria *(mandatory)*

- **SC-001**: From a freshly generated `dotnet new fs-skia-ui` project, an author
  (human or agent) can add a new control of a kind not shown in the starter using
  only the starter pattern and IntelliSense/bundled reference — with zero
  reflection calls and zero framework-source reads — and it compiles and renders.
- **SC-002**: 100% of public members of the Controls authoring surface carry a
  non-placeholder, non-empty XML doc summary; 0 members carry the known
  boilerplate sentence — verified by the new governance gate, which fails the
  build on any exception.
- **SC-003**: The generated template starter authors all of its controls through
  the typed Props front door (0 stringly legacy-builder control constructions in
  the demonstrated starter view), and compiles and renders with no behavior
  change versus today's starter.
- **SC-004**: Starting only from the generated project's README, a consumer
  reaches both the discovery API and a consumer-visible per-control catalog
  reference, and from either determines a named control's complete
  supported-attribute set without reflection.
- **SC-005**: Every place in the generated template that discourages reflection or
  source inspection resolves to a concrete, populated, consumer-visible
  alternative (typed starter, documented IntelliSense, discovery API, catalog
  reference) — i.e. no "do not reflect" instruction is left without a usable
  substitute.
- **SC-006**: The typed front door the starter relies on is present in the
  generated project's `docs/api-surface/` bundle and is covered by surface
  baselines, so it cannot silently drop out of the consumer-visible reference.

## Key Entities

- **Controls authoring surface**: the union of public members a consumer uses to
  author controls — legacy `Attr` builders, legacy per-control `create` entry
  points, typed `Props<'msg>` record fields and per-control `view` functions, the
  `Catalog` discovery API, and the interactive host entry point.
- **Typed Props front door** (`FS.Skia.UI.Controls.Typed`): per-control immutable
  `Props<'msg>` record + `view` function; the compiler-checked, discoverable
  authoring path; lowers structurally to the legacy lowered control IR.
- **Catalog facts**: per-control required attributes, supported attributes,
  supported events, visual states, and typed-module mapping — exposed both as data
  (`catalog.yml`) and programmatically (`Catalog` module).
- **Documentation-coverage gate**: new governance check enumerating the authoring
  surface and failing on placeholder/empty/duplicate-only documentation.
- **Generated project starter + README**: the consumer-facing entry points the
  template produces; the starter demonstrates the typed front door, the README
  points to the discovery mechanisms.

## Assumptions

- "Comprehensively with all fixes" is taken to mean all three diagnosed gaps are
  addressed together: (1) document the public authoring surface, (2) demonstrate
  and bundle the typed front door, (3) surface the per-control catalog facts and
  discovery API — plus a durable governance gate so the documentation cannot
  regress to boilerplate.
- Full documentation coverage applies to the **authoring** surface (what a
  consumer uses to build UIs). Purely internal modules (e.g. the internal lowering
  helpers) are out of scope, consistent with their internal visibility.
- The typed front door already lowers structurally to the legacy builders (proven
  by existing per-control parity tests), so migrating the starter to it is
  behavior-preserving; no new rendering evidence beyond "starter renders the same
  controls" is required.
- The interactive host seam in scope is the consumer-facing entry point already
  documented by the host skill; covering it means documentation + README
  reachability, not new host capability.
- Surfacing the per-control catalog reference to consumers means placing/duplicating
  it where the generated project can open it (alongside the existing
  `docs/api-surface/` bundle and/or product docs), not redesigning the catalog
  format.
- Migrating the remaining (non-starter) controls to the typed front door, and
  bundling the other capability packages' `.fsi` (Color, Input, SkillSupport)
  beyond what the controls-authoring story needs, are explicitly out of scope for
  this feature.
