# Feature Specification: Lookless Slot Composition

**Feature Branch**: `095-lookless-slot-composition`
**Created**: 2026-06-10
**Status**: Draft
**Input**: User description: "create the next part of docs/reports/2026-06-10-1010-controls-architecture-evolution-roadmap.md" — the controls architecture-evolution roadmap defines an E1→E5 evolution. E1 (feature 090, live event dispatch + the focus-aware text seam), E2 (features 091 + 092, the wired keyed reconciler + retained identity), E3 (feature 093, the visual-state / style layer), and E4 (feature 094, focus / keyboard traversal / input routing) have landed or are specified. The final rung is **E5 — lookless template / slot composition**, the one genuinely "XAML-flavored" capability the roadmap keeps, but reframed to stay declarative and inside the `Control<'msg>` IR.

## Context & Motivation *(informative)*

Every control kind in the catalog has a **fixed internal shape**. A `Button` renders box+label; a container renders its chrome the one way the kind's render branch hard-codes. A consumer can change a control's *tokens* (theme) and, after E3 (feature 093), its *style class / visual state* — but cannot change its *shape*: insert an icon before a button's label, replace a container's header region, or re-arrange a control's internal regions. That shape is baked into the kind, not exposed for composition.

The pieces in place today that E5 builds on:

- `Control<'msg>` (`src/Controls/Types.fsi:280`) is the immutable lowering target: a record of `Kind`, optional `Key` (`ControlId`), `Attributes` (`Attr<'msg> list`), `Children` (`Control<'msg> list`), optional `Content`, and `Accessibility`. A control's children are already arbitrary sub-trees of the **same** IR.
- `AttrValue<'msg>` (`Types.fsi:293`) already carries `ChildValue of Control<'msg>` and `ChildrenValue of Control<'msg> list` (`Types.fsi:309`–`310`), and E3 added `StyleClassesValue` / `VisualStateValue` by **riding the existing `Attr` mechanism under a category** (`AttrCategory.Style`, `Types.fsi:299`) rather than adding a top-level `Control` field. A slotted child can travel the same way — and therefore through the keyed reconciler diff.
- E2 (features 091 + 092) gives every control — including any sub-tree a consumer supplies — a **stable cross-frame retained identity** (`RetainedId`-keyed focus/text/clock state), so content placed in a slot keeps its focus/text/animation across an unrelated re-render.
- E3 (feature 093) resolves style declaratively; E4 (feature 094) delivers focus/keyboard for all controls. Content a consumer drops into a slot is itself a full `Control<'msg>`, so it composes with all of E1–E4 (its bindings dispatch, its style classes resolve, it can be focused/traversed) with no new machinery.

What is missing is the **slot mechanism**: a way for a control kind to declare a closed set of **named regions** a consumer may fill with their own `Control<'msg>` sub-tree, lowering to the same IR — so a consumer can re-skin a control's *shape*, not just its tokens.

E5 closes exactly this gap, and **only** this gap. It is the roadmap's deliberately-narrow, demand-gated final rung (`docs/reports/2026-06-10-1010-…-roadmap.md` §4 "E5 — optional, demand-driven" and §9 "Defer E5 until a real consumer needs lookless re-skinning"). The roadmap originally deferred it; this feature **implements** it and additionally adds consumer-facing capability guidance for the full E1–E5 surface (FR-010), and folding that deliverable in is the concrete trigger that ungated the rung. It is hard-bounded **away** from the rejected redesign: a slot is a static `Control<'msg>` value the consumer's own MVU `view` computes — **not** a data-bound `ControlTemplate` engine, **not** a `DataContext`, **not** a binding expression or per-item template instantiation. This is incremental MVU-core evolution toward declarative-retained (SwiftUI/Compose-class) capability parity per the maintainer architecture decision recorded 2026-06-10, not a redesign.

## Clarifications

### Session 2026-06-10

- Q: Is the slot set arbitrary (a consumer creates regions on any kind) or a closed, per-kind named set? → A: A **closed, per-kind named set**. A control kind declares a fixed set of named slots; a consumer fills only the slots a kind declares. There is no consumer-invented slot on a kind that declares none. This is the hard line that keeps slots from growing into a templating engine — mirroring E3's closed/ordered discipline.
- Q: What can fill a slot — a static `Control<'msg>` sub-tree, or a data-bound template? → A: A **static `Control<'msg>` sub-tree only**, computed by the consumer's own MVU `view` from `'model` and lowering to the same IR. No `DataContext`, no binding expression, no per-item template instantiation. The consumer's `view : 'model -> Control<'msg>` stays the single place model→view mapping happens; E5 introduces no second binding system.
- Q: Are slot names a typed/closed surface, or free-form like E3's free-form style-class escape hatch? → A: **Typed/closed per kind, with no free-form slot escape hatch** — deliberately stricter than E3's style classes. A free-form *style class* is safe (it resolves to token-derived values); a free-form *slot* on an arbitrary kind is exactly the lookless-`ControlTemplate` engine the roadmap permanently rejects, so slots stay typed and closed.
- Q: How are slots carried in the IR — a new top-level `Control` field, or the existing `Attr`/children mechanism? → A: The **existing `Attr` / `ChildValue` / `ChildrenValue` mechanism under a slot category**, mirroring how E3 rode `AttrCategory.Style`. A slotted child therefore travels through the keyed reconciler diff and keeps its E2 retained identity; **no** new top-level `Control` record field is added.
- Q: Does E5 expose slots on all 52 controls, or a representative set? → A: **Mechanism + a representative set** of slot-bearing kinds (concretely a leaf-with-regions kind — `Button` — and a composite-container kind), proving the mechanism end-to-end. A catalog-wide slot exposure of all 52 controls is explicitly out of scope and is a separate follow-up.
- Q: Should this feature also deliver consumer-facing capability guidance for the architecture-evolution series? → A: **Yes** — this feature additionally adds a **consumer-facing capability skill covering the full E1–E5 surface** (live event dispatch, retained identity, visual-state/style, focus/keyboard traversal, and slot composition). It is folded into feature 095 (not a separate feature), because the landed E1–E4 rungs (090–094) shipped without updating consumer guidance and the skills still teach the pre-E1 story.
- Q: Where does that skill live so a `dotnet new fs-skia-ui` consumer actually receives it? → A: By **expanding the package-owned + template-fragment consumer skills that ship into generated products** — `src/Controls/skill/SKILL.md` (`fs-skia-ui-widgets`) and `template/fragments/controls/skill/SKILL.md` (`fs-skia-generated-controls-guidance`). **No** new standalone `.agents/skills/<id>` governance skill is added (that audience is agent/repo-facing and does not ship into generated projects).
- Q: With the skill covering E1–E5 "fully", what is E5's implementation status here? → A: **E5 (the slot mechanism) is implemented as part of this feature** — it is **no longer demand-deferred**. Folding the consumer-skill deliverable in is the concrete trigger that ungates implementation, so the skill honestly documents E1–E5 as all-shipped capabilities (no Principle V synthetic-evidence disclosure for an unshipped feature).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A consumer re-skins a control's shape by filling named slots (Priority: P1)

A consumer authoring `view : 'model -> Control<'msg>` takes a slot-bearing control and supplies their own content for one of its **named** slots — for example puts an icon in a `Button`'s leading slot ahead of its label, or replaces a container's header region with a custom sub-tree — and the control renders with that content in that region, lowering to the same `Control<'msg>` IR.

**Why this priority**: Shape re-skinning is the entire E5 capability. Without it, a consumer who needs an icon-leading button or a custom container header has no declarative path short of authoring a whole new control.

**Independent Test**: Take a slot-bearing kind, fill one of its declared named slots with a known sub-tree, lower it, and assert the lowered `Control<'msg>` contains that sub-tree at the slot's position (and that filling a *different* declared slot places it in the *other* region) — using pure lowering, no live window required.

**Acceptance Scenarios**:

1. **Given** a slot-bearing control kind with a declared named slot, **When** a consumer supplies a `Control<'msg>` sub-tree for that slot and the control is lowered, **Then** the lowered IR contains the supplied sub-tree at that slot's region.
2. **Given** the same kind with two declared slots, **When** a consumer fills each with distinct content, **Then** each appears in its own region and the two do not collide or swap.
3. **Given** a kind that declares no slot of a given name, **When** a consumer attempts to fill that name, **Then** it is a compile-time error (typed, closed per-kind slot surface) — not a silently-ignored runtime no-op.

---

### User Story 2 - An unfilled control is byte-identical to today (Priority: P1)

A consumer who supplies **no** slot content gets exactly the control's current shape — the slot mechanism is additive and behavior-preserving. A maintainer can introduce slots on a kind without changing the render output of any existing consumer.

**Why this priority**: E5 is additive evolution, not a redesign. If exposing slots changed the default render, every existing consumer's output would shift — unacceptable. The behavior-preserving default is the safety property that lets E5 ship at all.

**Independent Test**: Render a slot-bearing kind with **no** slots supplied through the new mechanism and compare against a captured baseline of the same kind's prior (pre-slot) render for the same inputs; assert byte/structural-`Scene` equality. Repeat for a kind that has **not** been given slots and assert it is unchanged.

**Acceptance Scenarios**:

1. **Given** a slot-bearing kind with every slot left unfilled, **When** it is rendered, **Then** its output is byte-identical / structurally-`Scene`-equal to the kind's prior default shape (the slot's default content *is* today's chrome).
2. **Given** a control kind that has not been given slots, **When** it renders, **Then** it is unchanged — the slot mechanism is additive and partial, with no regression for kinds left as-is.
3. **Given** the `view : 'model -> Control<'msg>` consumer contract, **When** a consumer supplies no slots, **Then** the contract and behavior are identical to before E5.

---

### User Story 3 - Slotted content composes with E1–E4 and survives re-renders (Priority: P2)

A consumer drops an interactive sub-tree into a slot — say a button with an `onClick`, or a focusable, styled control — and that content behaves like any other control: its bindings dispatch (E1), its style classes resolve (E3), it is focusable/traversable (E4), and (because it is a real control in the retained tree) its focus/text/animation state survives an unrelated re-render (E2).

**Why this priority**: Slotted content that did *not* compose with the rest of the framework would be a dead region — a second-class sub-tree. Composition is what makes slots useful, but it depends on E1–E4, so it sequences after the two P1 capabilities.

**Independent Test**: Fill a slot with a control carrying an authored binding, a style class, and focusability; assert the binding dispatches the expected message, the style resolves via E3, and the control is reachable in the E4 tab order. Then apply an unrelated sibling-shifting model update (the 092 case) and assert the slotted control keeps its E2 retained identity (its focus/text is not reset).

**Acceptance Scenarios**:

1. **Given** a slot filled with a control that has an authored event binding, **When** that control is activated, **Then** its binding dispatches through the existing flat per-`ControlId` mechanism — slotted content is not a routing dead-zone.
2. **Given** a slot filled with a focusable, style-classed control, **When** the view is traversed and resolved, **Then** the slotted control appears in the E4 tab order and resolves its E3 style — composing with E1–E4 unchanged.
3. **Given** a slot filled with a stateful control (focused/with text), **When** an unrelated model update shifts siblings, **Then** the slotted control keeps its focus/text via E2 retained identity rather than being reset.

---

### User Story 4 - A template consumer receives capability guidance for the whole E1–E5 surface (Priority: P2)

A consumer who runs `dotnet new fs-skia-ui` (or an agent authoring against the package) opens the controls capability skill and finds honest, runnable guidance for the architecture-evolution capabilities that landed across E1–E5: how to dispatch events live (E1), why a control's focus/text survives a sibling-shifting re-render and how to key for it (E2 retained identity), how to attach style classes / variants and drive visual state (E3), how a control is focused and traversed by keyboard (E4), and how to fill a control's named slots to re-skin its shape (E5). The skill ships into generated products via the package-owned + template-fragment consumer skills.

**Why this priority**: The landed E1–E4 rungs (090–094) shipped without updating consumer guidance — the consumer skills still teach the pre-E1 "build `Control<'msg>` with `create` + attrs, keep state in the model" story and mention none of style classes, visual state, focus traversal, or retained-identity behavior. A template consumer therefore cannot discover capabilities the framework already has. This closes that gap, but it sequences after the slot mechanism itself (it documents E5, so the mechanism must exist first).

**Independent Test**: Open `src/Controls/skill/SKILL.md` and `template/fragments/controls/skill/SKILL.md` and confirm each names and shows a runnable consumer example for every rung E1–E5 (event dispatch, retained identity, style class/visual state, focus/keyboard, slot fill); confirm the `.agents`↔`.claude` peer is in sync (`SkillSyncCheck`) and the rubric passes (`SkillQualityCheck`); generate a project and confirm the selected Controls capability carries the updated guidance.

**Acceptance Scenarios**:

1. **Given** the package-owned and template-fragment consumer skills, **When** a consumer or agent reads them, **Then** each rung E1–E5 is named with a runnable consumer example, and the guidance is honest (a slot lowers to `Control<'msg>`; it is not a data-bound template).
2. **Given** the skill edits, **When** governance runs, **Then** `SkillSyncCheck` confirms the `.claude` peer matches the canonical source, `SkillQualityCheck` passes the rubric, and `GeneratedGuidanceCheck` is green.
3. **Given** a generated project that selects the Controls capability, **When** it is produced, **Then** it receives the updated E1–E5 consumer guidance.

### Edge Cases

- **A slot is left unfilled**: the control renders the slot's **default content** — exactly the kind's current chrome for that region — so an unfilled control is byte-identical to today (US2). A default is always defined; an unfilled slot is never a blank/hole.
- **A slot is filled with empty content** (an explicitly empty sub-tree / no children): the region renders empty *by the consumer's choice* — distinct from "unfilled" (which falls back to default). Filling with empty is an intentional override, not a fallback.
- **Same-kind controls in different slots**: two slot fills of the same control kind keep distinct retained identity via the keyed reconciler's key-first-then-positional rule (the 086/092 same-kind-sibling learning), so their focus/text do not cross-contaminate.
- **A consumer fills a slot the kind does not declare**: rejected at compile time by the typed, closed per-kind slot surface — never a silent runtime drop (US1 scenario 3). There is no free-form slot name.
- **Deeply-nested slotted content** (a slot fill that itself contains slot-bearing controls): lowers recursively to the same `Control<'msg>` IR with no special case; nesting is just ordinary tree composition, not template expansion.
- **A slot fill references the same `'msg` type**: slotted content is a `Control<'msg>` over the consumer's own message type, so its bindings dispatch into the consumer's single `update` — there is no separate template message channel or data context.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: A control kind MUST be able to declare a **closed, per-kind set of named slots** (regions a consumer may fill). The slot set is **fixed per kind and typed** so the authoring surface is compiler-checked; a consumer MUST NOT be able to create a slot on a kind that declares none, and there MUST be **no** free-form slot-name escape hatch (the deliberate divergence from E3's free-form style class — a free-form slot is the rejected templating engine).
- **FR-002**: A consumer MUST be able to **fill a named slot with a `Control<'msg>` sub-tree**, which MUST lower into the **same `Control<'msg>` IR** at the slot's region. The fill MUST be a static value the consumer's own `view : 'model -> Control<'msg>` computes from `'model`; E5 MUST NOT introduce a `DataContext`, a binding expression, or per-item template instantiation. The consumer's `view`/`update` stays the single model→view→message path.
- **FR-003**: An **unfilled slot MUST render the kind's default content** — exactly its current chrome for that region — so a slot-bearing control with **no** slots supplied is **byte-identical / structurally-`Scene`-equal** to the kind's prior (pre-slot) render. Exposing slots on a kind MUST be additive and behavior-preserving; kinds not given slots MUST be unchanged.
- **FR-004**: Slots MUST be carried on the **existing `Attr` / `ChildValue` / `ChildrenValue` mechanism under a slot category** (mirroring E3's `AttrCategory.Style`), NOT on a new top-level `Control` record field. A slotted child MUST therefore travel through the keyed reconciler diff and **keep its E2 retained identity**; E5 MUST NOT re-derive or alter the reconciler identity scheme established by features 067/091/092.
- **FR-005**: Slotted content MUST **compose with E1–E4 unchanged**: a binding inside slotted content MUST dispatch through the existing flat per-`ControlId` event mechanism (E1), its style classes/visual state MUST resolve through E3's single resolver, it MUST be focusable/traversable through E4's focus model when its `KeyboardOperation` declares it focusable, and its focus/text/animation state MUST survive an unrelated re-render via E2 retained identity. Slotted content MUST NOT be a routing/focus/style dead-zone.
- **FR-006**: Slot lowering MUST be **pure, total, and deterministic**: identical `(kind + slot fills)` inputs MUST always lower to an identical `Control<'msg>` IR, and lowering MUST never throw. The slot mechanism adds **no** new effect/command/subscription/interpreter behavior — it is structure that lowers to the existing IR.
- **FR-007**: E5 delivers the **slot mechanism + representative verification**, not a catalog-wide retrofit. The mechanism (slot declaration, fill, default fallback, lowering) MUST be general, but verification is bounded to a **representative set spanning the relevant families**: a **leaf-with-regions** kind (concretely **`Button`** — e.g. leading / label / trailing named slots) and a **composite-container** kind (a kind such as `Panel`/`SplitView`/`Dock` exposing named chrome regions; the exact kind and its slot names are a plan detail). A slot exposure of all 52 typed views is explicitly **out of scope** and is a separate follow-up.
- **FR-008**: The slot mechanism MUST be **additive** to the MVU consumer surface and MUST hold the permanent roadmap non-goals: **no** data-bound `ControlTemplate` engine, **no** `DataContext`, **no** binding expression / observable, **no** per-item template instantiation, **no** dependency/attached properties, **no** CSS-selector styling. The line is **"declarative, lowers to the `Control<'msg>` IR, no binding"**; anything that requires a runtime template-instantiation or data-binding context is out.
- **FR-009**: E5 is the roadmap's **optional final rung**, and the mechanism MUST stay minimal and MUST NOT speculatively grow toward the rejected templating engine. The roadmap originally **demand-gated** scheduling; folding the consumer-capability-skill deliverable (FR-010) into this feature is the concrete trigger that **ungates implementation**, so the slot mechanism is **implemented as part of feature 095** (no longer deferred). The bounded scope fixed by FR-001…FR-008 still pins the mechanism against scope-creep.
- **FR-010**: This feature MUST additionally deliver a **consumer-facing capability skill covering the full E1–E5 surface** as shipped capabilities: live event dispatch (E1), retained identity (E2, why focus/text survive a sibling-shifting re-render), style class/variant + visual state (E3), focus/keyboard traversal (E4), and slot composition (E5). Each rung MUST be named with a **runnable consumer example**, and the guidance MUST be **honest** — a slot lowers to `Control<'msg>` and is not a data-bound template; retained identity is a property of the keyed tree, not a binding. Because E1–E5 are all shipped by this feature (FR-009), **no** Principle V synthetic-evidence disclosure applies to the skill content.
- **FR-011**: The capability guidance MUST be delivered by **expanding the package-owned and template-fragment consumer skills that ship into generated products** — `src/Controls/skill/SKILL.md` (`fs-skia-ui-widgets`) and `template/fragments/controls/skill/SKILL.md` (`fs-skia-generated-controls-guidance`) — so a `dotnet new fs-skia-ui` consumer that selects the Controls capability receives it. The edits MUST keep the `.agents`↔`.claude` peers in sync (`SkillSyncCheck`), pass the skill-quality rubric (`SkillQualityCheck`), and keep `GeneratedGuidanceCheck` green. **No** new standalone `.agents/skills/<id>` governance skill is added (that audience does not ship into generated projects).

> Interacting / conflicting requirements: FR-002 (a consumer supplies an arbitrary `Control<'msg>` sub-tree) vs FR-008 (no templating/binding engine) — resolution: a slot accepts a **static** `Control<'msg>` *value* the consumer's own `view` already computed from `'model`, **not** a template instantiated per data item against a binding context; because model→view mapping stays in the consumer's single `view`, there is no second binding system, even though the supplied content is arbitrary.
> FR-001 (a kind exposes named slots) vs FR-003 (default render unchanged) — resolution: exposing a slot is additive; the slot's default content **is** today's chrome, so an unfilled control is byte-identical and existing consumers see no change.
> FR-001 (closed/typed slots, no free-form) vs E3's free-form style-class escape hatch (feature 093, FR-001) — resolution: deliberate divergence, not an inconsistency. Free-form *styling* resolves to safe token-derived values; a free-form *slot* on an arbitrary kind would be the lookless-`ControlTemplate` engine the roadmap rejects, so slots are held closed/typed while style classes stay open.

## Success Criteria *(mandatory)*

- **SC-001**: A consumer fills a declared named slot on a slot-bearing kind with a `Control<'msg>` sub-tree and the rendered control shows that content in the slot's region; filling two distinct slots places into two distinct regions — verified for 100% of the representative kinds' declared slots.
- **SC-002**: A slot-bearing control with **no** slots filled is byte-identical / structurally-`Scene`-equal to the kind's prior (pre-slot) render across the kind's states, and a control kind not given slots is unchanged — proving the mechanism is additive and behavior-preserving.
- **SC-003**: Slotted content composes with E1–E4: a binding inside slotted content dispatches exactly the expected message (E1), its style class/visual state resolves through E3's resolver, and a focusable slotted control appears in the E4 tab order — verified for a representative interactive slot fill.
- **SC-004**: Slotted content keeps its E2 retained identity across an unrelated re-render: a sibling-shifting model update (the 092 case) leaves a focused/with-text slotted control's focus/text intact, demonstrated through the live retained path rather than a hand-seeded map.
- **SC-005**: Slot lowering is pure and deterministic — identical `(kind, slot fills)` inputs lower to an identical `Control<'msg>` IR across at least 1000 generated input combinations, and lowering never throws (unfilled slots fall back to default, filled slots place the supplied sub-tree).

## Assumptions

- E2 (features 091 + 092) has landed: the keyed reconciler is on the live render path and confers the stable cross-frame retained identity (`RetainedId`-keyed focus/text/clock state) that slotted content attaches to. E5 consumes that identity and does not re-implement it.
- E3 (feature 093) provides the single state→style resolver so slotted content resolves its style by the same path as any control; E4 (feature 094) provides the focus model so a focusable slotted control is traversable. E5 composes with both; it adds no parallel style or focus path for slotted content.
- The `Control<'msg>` IR (`Kind`/`Key`/`Attributes`/`Children`/`Content`/`Accessibility`, `Types.fsi:280`) is the complete lowering target; slots ride the existing `Attr` / `ChildValue` / `ChildrenValue` mechanism under a slot category (as E3 rode `AttrCategory.Style`), so **no** new top-level `Control` record field is required.
- A slot fill is a static `Control<'msg>` value computed by the consumer's own MVU `view` from `'model`; the consumer's single `view`/`update` remains the only model→view→message path. This is a deliberate boundary, not an omission: it is what keeps E5 a composition mechanism rather than a binding/template engine.
- Per the architecture-evolution decision (2026-06-10), this is incremental MVU-core evolution toward declarative-retained parity (E-series), not a redesign; no data-binding, `DataContext`, `ControlTemplate`, dependency-property, or CSS-selector surface is introduced. E5 is the **one** "XAML-flavored" rung kept, reframed to stay declarative and inside the IR.
- E5 is the roadmap's **optional** final rung (`…-roadmap.md` §4, §9): the roadmap originally demand-gated its scheduling, but this feature **implements** it — folding in the consumer-capability-skill deliverable (FR-010) is the concrete trigger that ungated it. Like E1/E3/E4, it is scoped to **mechanism + representative verification**; a catalog-wide slot exposure of all 52 controls is a separate follow-up.
- The package-owned + template-fragment consumer skills are the channel that ships guidance into generated products; expanding them (not adding a new `.agents/skills/<id>`) is what makes the E1–E5 guidance reach an actual `dotnet new fs-skia-ui` consumer. E1–E4 are already landed (090–094) and E5 lands in this feature, so the skill documents all five as shipped capabilities with no synthetic-evidence disclosure.

## Key Entities

- **Named slot**: a per-kind, closed, typed region a control kind declares as consumer-fillable (e.g. a `Button`'s leading / label / trailing). The unit of lookless re-skinning.
- **Slot fill**: the consumer-supplied `Control<'msg>` sub-tree placed into a named slot, lowering to the same IR; a static value the consumer's own `view` computes from `'model`.
- **Default slot content**: the kind's current chrome for an *unfilled* slot — the behavior-preserving base that makes an unfilled control byte-identical to today.
- **Slot-bearing kind**: a control kind that declares named slots; the representative set is a leaf-with-regions kind (`Button`) and a composite-container kind (a `Panel`/`SplitView`/`Dock`-class container; exact kind a plan detail).
- **Slot lowering**: the pure, total, deterministic mapping of `(kind + slot fills) → Control<'msg>` IR, riding the existing `Attr` / `ChildValue` / `ChildrenValue` mechanism under a slot category — the lowering target through which slotted content inherits E1–E4 behavior and E2 identity.
- **Consumer capability skill**: the package-owned + template-fragment consumer guidance (`src/Controls/skill/SKILL.md`, `template/fragments/controls/skill/SKILL.md`) expanded to teach the full shipped E1–E5 surface with runnable examples — the channel by which a `dotnet new fs-skia-ui` consumer discovers the architecture-evolution capabilities.
