Extended investigation, 2026-05-28:
- The failure is not caused by the major version number in `fake-cli` 6.1.4 meaning "requires .NET SDK 6".
- Installing .NET SDK 6.0.428 did not fix the failure by itself.
- Host tracing showed the first FAKE SDK probe uses `/home/developer/.dotnet/dotnet` and resolves SDK `10.0.300` successfully.
- The later FAKE runtime resolver probe enumerates Linux's default dotnet install root and invokes `/usr/share/dotnet/dotnet --version`.
- `/usr/share/dotnet` exists but has no `sdk` directory; it contains only host/runtime assets. That absolute host therefore exits with code 155 and "No .NET SDKs were found".
- FAKE 6.1.4 upstream source confirms this behavior: `SdkAssemblyResolver.ResolveDotNetRoots()` collects environment candidates, PATH candidates, and the default Linux candidate `/usr/share/dotnet/dotnet`, then `ResolveSdkRuntimeVersions()` runs `DotNet.getVersion` for each collected root. A broken default root can fail the whole resolver even when `PATH` and `DOTNET_ROOT` point to a valid SDK install.

Verified local workaround:
- `FAKE_SDK_RESOLVER_CUSTOM_DOTNET_PATH=/home/developer/.dotnet /tmp/fake614-tool/fake run /tmp/fake-investigate/native-target.fsx --list`
- Result: passed and listed the minimal native target `A`.
- Note: despite the environment variable name saying "PATH", FAKE 6.1.4 treats this value as a dotnet root directory and appends `/dotnet`; setting it to `/home/developer/.dotnet/dotnet` fails by trying `/home/developer/.dotnet/dotnet/dotnet`.

Remaining remedies:
- Set `FAKE_SDK_RESOLVER_CUSTOM_DOTNET_PATH=/home/developer/.dotnet` in the FAKE invocation environment before attempting native target registration again.
- Or install a full SDK under `/usr/share/dotnet` so the default Linux candidate is valid.
- Or remove/replace the runtime-only `/usr/share/dotnet` host from the resolver's reachable installation roots.
- Or keep the current custom runner and avoid FAKE's Paket script dependency resolver for this feature.
