# Data Model: Asteroids Feedback Skill Guidance

## Skill Assignment Rule

- **Fields**: `task_category`, `trigger_context`, `required_skill_ids`, `advisory_skill_ids`, `ordering_reason`, `no_skill_rationale`
- **Relationships**: maps a generated task to one or more local `SKILL.md` files through `tasks.deps.yml` `skillist` metadata and the visible `tasks.md` mirror.
- **Validation rules**: Mandatory local skills remain blocking when existing governance requires them. FS.Skia.UI capability hints are advisory unless a task directly matches a skill description. Multiple skills must be minimal, ordered, and mirrored exactly.

## Generated Visual Demo Task

- **Fields**: `task_id`, `story_id`, `title`, `description`, `skillist`, `visible_skillist_mirror`, `readiness_outputs`, `acceptance_cues`
- **Relationships**: belongs to a generated `tasks.md` story group; may produce readiness evidence and may depend on implementation, layout, verification, or audit tasks.
- **Validation rules**: Rendering, screenshot capture, layout readability, persistent launch, deterministic evidence mode, generated-package validation, and debug-until-green tasks must either list the relevant skill ids or explain why no specialized skill applies.

## Readiness Scaffold

- **Fields**: `path`, `owner_task_id`, `required_terms`, `required_key_values`, `artifact_paths`, `authoritative_command`, `failure_classification`, `next_action`
- **Relationships**: one scaffold belongs to the generated demo feature readiness directory and supports one or more audit checks.
- **Validation rules**: Generated visual demo tasks must enumerate readiness files for visual evidence, window visibility, close-reason separation, window-state diagnostics, window options, governance risk levels, aggregate hang diagnostics, runtime limitations, generated validation, and real-image evidence when those obligations apply.

## Visual Proof Claim

- **Fields**: `claim_type`, `artifact_path`, `report_path`, `is_decodable_image`, `width`, `height`, `content_classification`, `renderer_mode`, `fallback_used`, `unsupported_reason`
- **Relationships**: referenced from readiness evidence and acceptance criteria; may be produced by screenshot, scene evidence, image evidence, or layout evidence tasks.
- **Validation rules**: Screenshot proof requires a decodable image at the claimed artifact path, expected dimensions, and non-trivial content. Metadata-only reports, fallback or placeholder images, and layout-only bounds checks are incomplete or unsupported visual proof unless they independently satisfy the same image checks.

## Feedback Finding

- **Fields**: `finding_id`, `source_report`, `summary`, `owner_category`, `evidence_quote_or_observation`, `follow_up_path`, `deferred_scope`
- **Relationships**: derived from `Mailbox/2026-05-30T07-19-26+0200-asteroids-demo-implementation-phase-fs-skia-ui-feedback.md`; may map to a framework runtime backlog, template/evidence workflow change, documentation/discoverability work, or consumer-authoring guidance.
- **Validation rules**: Owner category must be one of `framework-runtime`, `generated-template-evidence-workflow`, `documentation-discoverability`, or `consumer-authoring`. Runtime fixes remain deferred unless separately specified.

## Guidance Scan Result

- **Fields**: `scan_path`, `scan_command`, `required_topic`, `observed_terms`, `missing_terms`, `advisory_only`, `status`, `next_action`
- **Relationships**: produced by governance tests or generated guidance checks; supports `generated-guidance-validation.md`.
- **Validation rules**: Scans must prove that skill assignment, multiple-skill guidance, readiness scaffolding, visual evidence honesty, and owner classification are visible before implementation begins.

## Public FSI Documentation Surface

- **Fields**: `project_path`, `package_id`, `assembly_name`, `fsi_path`, `public_member_id`, `member_kind`, `summary`, `parameters`, `returns`, `remarks_or_examples`, `documentation_status`
- **Relationships**: belongs to a packable `src/*/*.fsproj`; maps `.fsi` public signatures to generated XML documentation member entries.
- **Validation rules**: Every public module, type, union case, record, field, and value compiled from packable framework `.fsi` files must have a non-empty summary. Functions and members with parameters require parameter documentation where applicable. Non-obvious modules, workflows, and factory functions require remarks or examples. Runtime API shapes remain unchanged unless a separate design pass updates the `.fsi` contract.

## XML Documentation Artifact

- **Fields**: `package_id`, `assembly_name`, `build_output_xml_path`, `nupkg_path`, `packed_xml_entry`, `member_count`, `documented_member_count`, `missing_members`, `status`, `next_action`
- **Relationships**: generated by packable framework project builds and included in corresponding packed NuGet artifacts.
- **Validation rules**: The generated XML documentation file must exist, be non-empty, contain member documentation for the public `.fsi` surface, and be present in each packed NuGet artifact with the assembly-corresponding XML file name.
