# Contract: Feedback Classification

## Scope

Asteroids implementation feedback is classified before follow-up work is created.

## Required Behavior

- Each finding from the Asteroids implementation-phase report receives exactly one primary owner category.
- Valid owner categories are `framework-runtime`, `generated-template-evidence-workflow`, `documentation-discoverability`, and `consumer-authoring`.
- Runtime package behavior fixes remain deferred unless a later feature specification explicitly scopes them in.
- Follow-up tasks name the owner category, source report, evidence observation, and bounded next action.

## Acceptance Cues

- Framework-runtime examples include offscreen stroke rasterization, offscreen text rasterization, screenshot artifact honesty, fallback-image proof contracts, host-size delivery, and persistent-launch smoke ergonomics.
- Generated-template/evidence workflow examples include hidden readiness contract scaffolding and generated evidence acceptance wording.
- Documentation/discoverability examples include shipped XML API surface docs, public capability references, package documentation validation, and name-collision guidance.
- Consumer-authoring examples include the initial headless-host misclassification, choosing stroke-only entities without fallback evidence, and benign warning classification.
