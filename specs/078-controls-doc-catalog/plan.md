# Implementation Plan: Authoritative Controls Catalog in Published Docs

**Branch**: `078-controls-doc-catalog` | **Date**: 2026-06-08 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/078-controls-doc-catalog/spec.md`

## Summary

Add a new top-level **"Controls" section** to the published fsdocs/GitHub Pages
site that gives app developers a single authoritative answer to "what controls
exist and what does each do?" — comparable to Avalonia's Controls reference. The
section is ordered: a **Spec Kit usage narrative** (with a **Penpot/design-token
subsection**) → a **generated catalog index** listing all 52 supported controls
grouped by category → **one hand-authored detail page per control**, each carrying
prose, a usage example where the catalog has one, a **rendered preview image**, and
a link to its generated API reference page.

Technical approach, reusing existing single-source machinery:

- The **catalog index** and each detail page's **canonical header** (name,
  category, API link) are *generated* from the existing single source
  `CatalogGen.catalogFacts` (52 rows) via the same `BEGIN/END GENERATED` splice-marker
  pattern already used for `src/Controls/catalog.yml` and `src/Controls/Catalog.fs`,
  and regenerated by `RefreshSurfaceBaselines`. Hand-authored prose/usage lives
  *outside* the generated regions.
- **Per-control preview PNGs** are produced through the existing deterministic
  render-only evidence path and committed as docs **source** assets under
  `docs/img/controls/`. The docs CI job stays GPU-free; it copies the committed
  PNGs. Where a control cannot be honestly rendered, the detail page states that
  explicitly (no placeholder/1×1 image — forbidden by visual-proof honesty rules).
- A new currency gate **`ControlsCatalogDocsCheck`** fails when the generated index
  drifts from `catalogFacts`, a supported control lacks its required detail page (or
  an orphan page/preview survives a removed control), a required preview is
  missing/stale/undecodable, or a generated cross-link does not resolve.

No public `.fsi` surface, package identity, or runtime behavior changes. This is a
docs-content + governance-generation feature.

> **Count note**: "52" throughout this plan is the *current* `catalogFacts`
> supported count, used illustratively. The authoritative count is whatever
> `catalogFacts` holds at generation time; `FR-010`/`SC-002` and
> `ControlsCatalogDocsCheck` enforce the live value, so the literal here never
> becomes the source of truth.

> **Requirements traceability**: the generated catalog index satisfies
> `FR-001`/`FR-004`/`FR-010` (`SC-001`/`SC-002`); per-control detail pages satisfy
> `FR-002`/`FR-003`/`FR-008` (`SC-003`); rendered previews satisfy `FR-003a`
> (`SC-003`); the `ControlsCatalogDocsCheck` currency gate satisfies `FR-005`
> (`SC-004`); the usage narrative + Penpot subsection + cross-links satisfy
> `FR-006`/`FR-007`/`FR-009` (`SC-005`/`SC-006`).

## Technical Context

**Language/Version**: F# / .NET `net10.0` (governance generators + currency check in
`FS.Skia.UI.Build` under `build/Governance/**`); Markdown + literate `.fsx` docs
content under `docs/`.
**Primary Dependencies**: fsdocs (FSharp.Formatting) CLI pinned in
`.config/dotnet-tools.json`; SkiaSharp render-only path via `FS.Skia.UI.SkiaViewer`
+ `FS.Skia.UI.Testing` for preview generation/validation. No new packages.
**Testing**: Expecto governance tests in `FS.Skia.UI.Build` tests (currency,
generation byte-identity, link resolution); `dotnet fsdocs build --strict --eval`
for site build; reuse of `Testing` PNG-validation (`readPngArtifact`) for preview
honesty.
**Target Platform**: Windows and Linux. Preview *rendering* requires a
render-capable host (GPU-passthrough dev environment or off-screen raster);
preview *consumption* (docs build) is platform-neutral and GPU-free.

### Repository Governance Decisions

- **Template ownership**: N/A — no `.template.config/template.json` change. This
  feature touches the repository's *own* published docs (`docs/**`), its governance
  build (`build/Governance/**`), and a new gate; it ships nothing into the
  `dotnet new fs-skia-ui` template and changes no template source, samples, package
  policy, or command surface that the template embeds.
- **Dependency impact**: N/A — no new dependency. `Directory.Packages.props`,
  `docs/dependencies.md`, generated template inclusion, and `DependencyReport`
  coverage are unchanged; preview generation reuses already-pinned SkiaSharp via the
  existing `SkiaViewer`/`Testing` packages, and docs reuse the already-pinned fsdocs
  tool.
- **Command-surface impact**: **Changes required.** Add a new FAKE target
  `ControlsCatalogDocsCheck` (registered in `build/Governance/Targets.fs`, routed in
  `Routing.fs`, interpreted in `Engine/Update.fs`, listed in
  `AgentValidation.knownGates`); extend the `RefreshSurfaceBaselines` handler to
  regenerate the catalog index + detail-page header regions. `validation.contract.yml`
  is regenerated from `Routing.fs` (not hand-edited; `TargetMetadataDrift` enforces
  currency). `Dev`, `Verify`, `Ci`, `PackLocal`, `TemplateCheck`, `DependencyReport`,
  `TemplateDrift`, `EvidenceGraph`, `EvidenceAudit` do not change behavior. FAKE-backed
  targets are run sequentially in deterministic order. Steps 1–4 are the minimal
  inner subset for iterating on the gate; the full serialized governance order
  (adding the merge-gate steps 5–6) is authoritative in `tasks.md` (Canonical
  Verification Targets):
  1. `./fake.sh build -t Route`
  2. `./fake.sh build -t Dev`
  3. `./fake.sh build -t ControlsCatalogDocsCheck`
  4. `./fake.sh build -t GeneratedGuidanceCheck`
  5. `./fake.sh build -t EvidenceGraph`
  6. `./fake.sh build -t EvidenceAudit`
- **Generated project impact**: N/A — no change to default/minimal generated
  contents, selected Controls guidance, generated local skills, validation logs,
  placeholder/excluded-history scans, or generated `Dev` behavior. The new docs live
  in this repo's site, not in generated projects.
- **Evidence paths**: Readiness evidence under
  `specs/078-controls-doc-catalog/readiness/`:
  - `controls-catalog-docs.md` — `ControlsCatalogDocsCheck` PASS/FAIL report (index
    currency vs. `catalogFacts`, detail-page completeness, preview present/current/
    decodable, link resolution).
  - `controls-preview-evidence.md` — per-control preview render honesty record
    (decodable image, dimensions, non-trivial content, renderer mode, fallback
    classification, and explicit unsupported reason for any control that cannot be
    rendered).
  - `docs-build.md` — `dotnet fsdocs build --strict --eval` success + presence of the
    index, detail pages, and previews in `output/`.
  - Generated docs source artifacts: `docs/controls/catalog.md` (generated region),
    `docs/controls/<id>.md` (generated header region), `docs/img/controls/<id>.png`.
- **`.fsi` / contract impact**: N/A — no public `.fsi` signatures, public docs of
  public types, surface baselines, sample contracts, or compatibility notes change.
  Generation/checks *read* the existing public control surface and `catalogFacts`;
  they do not redefine it. (Governance build code in `FS.Skia.UI.Build` has its own
  internal `.fsi` files that may gain the new module's signature; that is build-tool
  internal surface, not product public contract.)
- **MVU/effect boundary**: N/A as a *runtime* concern — no framework `Model`/`Msg`/
  `Effect`/`update` changes. The new generator and currency check follow the
  governance engine's existing pure-core/edge-interpreter shape: pure functions
  compute generation output and currency drift; the `Engine/Update.fs` handler
  performs file reads/writes and `FailWith` only at the edge, mirroring the existing
  `ControlsCatalogGenerationCheck` handler.
- **Synthetic evidence**: Identified risk — per-control preview PNGs cannot be
  rendered in the GPU-free docs CI. Resolution avoids synthetic evidence: previews
  are pre-rendered through the **real** deterministic render-only path on a
  render-capable host and committed as source assets; the docs build only consumes
  them. A control that genuinely cannot be honestly rendered carries an explicit
  honest *unsupported* note (not a fabricated/1×1 placeholder — both are rejected by
  the visual-proof rules), which is an honest declaration, not synthetic evidence. If
  any individual preview must be deferred, its task is marked `[S]` with full
  Principle V disclosure and a named real-evidence path; no `[S]` may remain at merge.
- **Test evidence**: Failing-first governance tests in the `FS.Skia.UI.Build` test
  project: (a) index generator round-trip/byte-identity vs. `catalogFacts`; (b)
  currency check FAILs on a stale index, a missing detail page, an orphan
  page/preview, a missing/undecodable preview, and a dead generated link, and PASSes
  on a clean tree; (c) detail-page header-region splice idempotence. Plus
  `RefreshSurfaceBaselines` regen produces a clean tree, and `dotnet fsdocs build
  --strict --eval` succeeds with the new pages/assets present.
- **Observability**: The `ControlsCatalogDocsCheck` report names each failing
  condition with an actionable remedy and the regenerate command
  (`./fake.sh build -t RefreshSurfaceBaselines`); missing required artifacts fail
  loudly via `RequireFiles`. Preview validation distinguishes a genuinely
  non-renderable control (honest unsupported message) from a real `RenderingFailure`,
  preserving real diagnostics per the evidence-mode benign/blocking rules.
- **Deferred scope**: No new controls, no control-behavior or visual-redesign work,
  no docs-theme redesign, no API-reference-generator redesign, no release/
  distribution/platform changes, no live Penpot/MCP integration (documented only).
  Any preview that cannot be honestly produced in this iteration is a bounded,
  disclosed `[S]` follow-up, not silent omission.
